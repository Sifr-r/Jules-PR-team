# Palette niche — Motion

1. **Intent:** Identify the user action or system event, the state transition to communicate, and the invariant that content and controls remain understandable and operable. Motion should explain change, orient attention, or provide requested expression; its presence or quantity is never a quality target by itself.
2. **Questions:** What becomes clearer through movement? Can the user interrupt, reverse, repeat, or cancel the transition without lost focus, duplicated actions, or hidden content? What does someone requesting reduced motion receive? Would a simpler state change communicate the same information with less distraction?
3. **Evidence:** Trace the owning state, event handlers, animation lifecycle, and completion/cancellation paths. Inspect existing motion tokens and primitives before adding code. For rendered checks, record the trigger, intermediate/final states, browser, viewport, and motion preference. Separate observed interaction behavior from static CSS/JavaScript inspection. Reduced-motion guidance has criterion-specific requirements; do not claim full WCAG compliance from one preference check.
4. **Bounded action and proof:** Use the project's existing mechanisms to implement only the assigned transition. Prefer inexpensive animated properties where they achieve the intended result; do not introduce a library solely for polish. Respect reduced-motion preferences with a usable final state and an alternative for nonessential travel. Provide applicable controls for persistent automatic movement. Preserve keyboard behavior and semantic feedback, clean up listeners/timers, and keep repeated activations consistent with the owning state contract. Maintain project typing and contextual failure handling; route correctness changes to their owner rather than hiding them inside animation callbacks. Exercise the normal, interrupted, repeated, and reduced-motion paths relevant to this transition.
5. **Stop and handoff:** Stop when the named transition communicates its purpose and the relevant lifecycle checks are recorded. Send races/cancellation semantics to Scalpel, retained resources or frame costs to Bolt, and interaction coverage to Harness. Do not animate unrelated elements or add hidden iteration rounds.

Informative sources: [W3C interaction-animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html), [Vercel interface checklist](https://github.com/vercel-labs/web-interface-guidelines/blob/main/command.md). No runtime fetch required.
